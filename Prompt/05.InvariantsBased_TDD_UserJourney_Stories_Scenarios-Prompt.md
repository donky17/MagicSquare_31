## # Level 1: Epic — Business Goal

## 1. Epic Title
**불변식 기반 사고 훈련 시스템 구축 (4x4 Magic Square TDD Practice)**

## 2. Business Goal
4x4 Magic Square 문제를 매개로, 학습자가 **불변식(Invariant) 중심으로 설계하고 이를 계약(Contract)과 테스트(Test)로 고정**한 뒤 구현/리팩토링까지 일관되게 수행할 수 있는 **훈련용 학습 시스템(과제/가이드/평가 기준)** 을 구축합니다.

## 3. Learning Goal
학습자가 다음 역량을 반복 훈련하여 체득합니다.
- **불변식 중심 설계 사고**: “정답”이 아니라 “항상 참이어야 하는 규칙”을 먼저 세운다
- **Dual-Track TDD 적용**: UI/입출력 경계(Contract)와 Domain Logic(Invariant)을 분리해 각각 TDD로 진행한다
- **입력/출력 계약 명확화**: 유효성, 에러 모델, 메시지/형식 등 경계를 테스트 가능한 계약으로 정의한다
- **설계 → 테스트 → 구현 → 리팩토링** 루프를 유지하면서도 계약을 깨지 않는다
- **Concept → Invariant → Contract → Test** 간 **추적성(Traceability)** 을 유지한다

## 4. Problem Statement
TDD 연습이 “테스트 작성 기술”이나 “코드 구현”으로만 흐르면,
- 무엇을 **불변식으로 고정해야 하는지**가 불명확해지고
- 입력 검증/에러 처리 같은 **경계 계약이 흔들리며**
- 리팩토링 중 **외부 계약이 무의식적으로 변경**되는 문제가 반복됩니다.

따라서 4x4 Magic Square를 통해, 정답 풀이가 아니라 **불변식과 계약을 중심으로 설계·검증·리팩토링하는 사고 체계**를 훈련할 수 있는 명확한 Epic 수준의 목표와 기준이 필요합니다.

## 5. Target Learners / Users
- **주 대상**: TDD를 알고는 있으나 “무엇을 테스트해야 하는지/무엇이 안정점인지”가 흔들리는 개발자
- **부 대상**: 설계를 먼저 고정하고(불변식/계약) 구현은 교체 가능하게 만들고 싶은 개발자/팀
- **사용 맥락**: 개인 훈련, 스터디, 사내 교육(과제 기반)

## 6. Scope
Epic 범위에서 포함할 것(“무엇을 달성해야 하는가” 수준)
- **4x4 Magic Square 도메인 규칙을 불변식으로 정리**하고, 그 불변식이 **테스트로 추적 가능**하도록 학습 흐름을 설계
- **입력/출력 계약(경계)** 을 명시하고, **Boundary 검증 계약 테스트가 100% 통과**하도록 품질 기준 정의
- **Dual-Track(Logic vs UI/IO)로 TDD를 진행**하도록 학습 구조/평가 기준 정립
- **리팩토링 안전장치**: 리팩토링 이후에도 **외부 계약은 불변**이어야 한다는 원칙을 강제
- “매직 넘버 금지/명명된 상수 사용/하드코딩 금지” 등 **코딩 규율을 평가 기준에 포함**(구현은 Level 2+에서 다룸)

## 7. Non-Scope
Epic 범위에서 제외(아직 하지 않을 것)
- 특정 언어/프레임워크/테스팅 도구의 선택 및 구현 세부
- 구체 UI 설계(화면 구성, 컴포넌트 구조) 및 실제 UI 구현
- 알고리즘 최적화, 성능 튜닝, 배포/운영
- Level 2(User Story) 및 Level 3(Task) 상세 분해와 실행 계획
- 정답 생성 로직의 구체 알고리즘 채택(백트래킹 등)과 구현 전략 확정

## 8. Success Criteria
품질/학습 목표를 **검증 가능한 기준**으로 고정합니다.
- **Domain Logic 테스트 커버리지 95% 이상**
- **Boundary 입력 검증 계약 테스트 100% 통과**
- **설명 없는 매직 넘버 금지**
- **명명된 상수 사용**: `GRID_SIZE`, `MAX_VALUE`, `MAGIC_CONSTANT` 등 (명칭은 예시이며 “의미 기반 상수화”가 핵심)
- **정답 하드코딩 금지**
- **주요 Invariant는 최소 1개 이상의 테스트로 추적 가능**
- **리팩토링 후에도 외부 입력/출력 계약은 변경되지 않음**

## 9. Key Invariants
(구현 방식과 무관하게 “항상 유지되어야 하는 규칙” 후보를 Epic 수준에서 명시)
- **I1. Grid 구조 불변식**: 그리드는 \(4 \times 4\) 이며, 셀 수는 16이다
- **I2. 값의 도메인 불변식**: 사용/생성되는 값은 허용된 범위 및 타입을 만족해야 한다 (예: 정수, 범위 제한)
- **I3. 유일성 불변식**: 허용된 값들은 중복 없이 사용되어야 한다 (문제 정의가 “1..16을 한 번씩”이라면 이를 불변식으로 고정)
- **I4. 합(매직 상수) 불변식**: 각 행/열(및 채택 시 대각선)의 합은 동일한 매직 상수를 만족한다
- **I5. 매직 상수 정의 불변식**: 매직 상수는 “격자 크기와 값 집합”으로부터 **유도**되며 임의 숫자(매직 넘버)로 취급되지 않는다
- **I6. 경계 계약 불변식**: 잘못된 입력은 “정해진 방식”으로 거부/에러 처리되며, 그 형식은 리팩토링 후에도 바뀌지 않는다
- **I7. 추적성 불변식**: 각 핵심 불변식은 최소 하나 이상의 테스트로 연결되어 “왜 이 테스트가 존재하는지”가 설명 가능해야 한다

## 10. Traceability Rule
- **규칙**: 모든 핵심 개념은 다음 체인으로 추적 가능해야 합니다.  
  **Concept → Invariant → Contract → Test**
- **최소 요건**:
  - 각 **Invariant**는 고유 식별자(예: `INV-ROW-SUM`, `INV-UNIQUE-VALUES`)를 가진다
  - 각 **Contract**(입력/출력 규칙)는 어떤 Invariant를 보호/노출하는지 명시한다
  - 각 **Test**는 어떤 Contract/Invariant를 검증하는지 연결된다
- **변경 규칙**:
  - 리팩토링은 허용되나 **Contract는 변경 불가**
  - Invariant 변경이 필요하면, 그 사유는 Concept 레벨로 거슬러 올라가 재정의되어야 한다(임의 수정 금지)

## 11. Candidate User Stories for Level 2
(아직 분해/Task화하지 않고, 다음 단계로 자연스럽게 도출될 수 있는 후보만 제시)
- **US-1**: 학습자로서 4x4 Magic Square의 핵심 **Concept/Invariant 목록**을 합의된 포맷으로 정리하고 싶다
- **US-2**: 학습자로서 각 Invariant를 보호하는 **입력/출력 Contract**를 명시하고 싶다
- **US-3**: 학습자로서 Contract를 위반하는 입력을 체계적으로 나열해 **Boundary 검증 기준**을 확정하고 싶다
- **US-4**: 학습자로서 Invariant와 Contract가 테스트로 어떻게 연결되는지 **Traceability 매핑**을 만들고 싶다
- **US-5**: 학습자로서 Domain Logic과 UI/IO 경계를 분리해 **Dual-Track TDD 흐름**으로 진행하고 싶다
- **US-6**: 학습자로서 “매직 넘버 금지/상수 명명/하드코딩 금지”가 **품질 기준**으로 강제되는 형태로 연습하고 싶다
- **US-7**: 학습자로서 리팩토링 이후에도 Contract가 유지되는지 확인하는 **회귀 기준**을 갖고 싶다

## 4. Detailed Journey

### Stage 1: Problem Recognition
- **Action:**
  - 주어진 규칙을 “해결 절차”가 아니라 “항상 유지되어야 하는 불변식”으로 재표현한다.
  - 입력/출력 요구사항을 **경계 계약 후보**로 분리해 메모한다(아직 확정은 Stage 2).
- **Thinking:**
  - “정답을 맞히는 알고리즘”보다 “입력과 출력 사이에서 절대 깨지면 안 되는 규칙”을 먼저 고정해야 한다.
  - 4x4 마방진 상수 34는 구현 상수가 아니라 **도메인 상수**로 취급되어야 한다.
- **Emotion:**
  - 초반엔 “빨리 풀고 싶다”는 조급함, 이후엔 “규칙이 선명해지니 안정감”으로 전환.
- **Pain Point:**
  - 규칙이 많아 보여서 어디까지가 핵심 불변식인지 흐려짐.
  - “조합을 바꿔 시도한다” 같은 절차 규칙이 도메인 규칙과 섞여 혼란.
- **Opportunity:**
  - **불변식(도메인 규칙) vs 계약(경계 규칙) vs 전략(시도 순서)**를 분리하면 이후 설계가 단순해진다.
- **Related Invariant:**
  - **INV-GRID-4x4**: 입력은 4x4 정수 행렬
  - **INV-BLANK-COUNT-2**: 0(빈칸)은 정확히 2개
  - **INV-VALUE-RANGE**: 값은 0 또는 1~16
  - **INV-UNIQUE-NONZERO**: 0 제외 중복 불가
  - **INV-MAGIC-CONSTANT-34**: 4x4 마방진 상수는 34
  - **INV-COORD-1INDEX**: 좌표는 1-index 기준(출력 계약과 결합되는 불변식)
- **Expected Learning Outcome:**
  - “문제 = 알고리즘”이 아니라 **문제 = 불변식 + 계약 + 전략**으로 재인식한다.
  - 불변식이 **테스트가 보호해야 할 대상**임을 명확히 한다.

---

### Stage 2: Contract Definition
- **Action:**
  - 입력/출력/오류 계약을 **검증 가능한 문장**으로 확정한다(예: 허용/거부 조건, 오류 형태).
  - “유효하지 않은 입력이면 무엇을 반환/보고하는가”를 먼저 결정한다.
- **Thinking:**
  - Domain은 “올바른 입력에서 올바른 출력”만이 아니라, **경계에서 잘못된 입력을 거부하는 계약**이 있어야 TDD가 흔들리지 않는다.
  - 출력이 `int[6]`이고 좌표가 1-index이며 포맷이 `[r1,c1,n1,r2,c2,n2]`라는 점은 **외부 계약**으로 고정해야 한다.
- **Emotion:**
  - 처음엔 제약이 많아 답답, 계약이 정리되면 리팩토링에 대한 두려움이 줄어듦.
- **Pain Point:**
  - 오류 정책이 모호하면 테스트가 “원하는 대로” 바뀌며 추적성이 무너짐.
  - 입력 오류와 “조합 실패(유효 입력이지만 해가 없음)”가 섞이기 쉬움.
- **Opportunity:**
  - **Input Error vs No-Solution**을 계약으로 분리하면, UI/Boundary와 Solver의 책임이 자연스럽게 분리된다.
- **Input Contract:**
  - 입력은 **4x4 `int` 행렬**이어야 한다.
  - 각 원소는 **0 또는 1~16**이어야 한다.
  - **0은 정확히 2개**여야 한다.
  - **0을 제외한 값은 중복 불가**여야 한다.
  - 위 조건을 하나라도 위반하면 **입력 오류로 처리**한다(오류 계약으로 연결).
- **Output Contract:**
  - 출력은 **길이 6의 `int[6]`**이다.
  - 포맷은 **`[r1, c1, n1, r2, c2, n2]`**이다.
  - 좌표 `(r, c)`는 **1-index**이며 각각 **1~4** 범위다.
  - `n1`, `n2`는 **0이 아닌 값**이며 입력의 빈칸(0) 위치에 채워지는 값이다.
  - “작은 누락 숫자를 첫 번째 빈칸, 큰 누락 숫자를 두 번째 빈칸”을 **첫 시도 규칙**으로 취급하되, 이는 Solver의 전략으로 Stage 3/4에서 책임을 둔다.
- **Error Contract:**
  - **Input Error**: 입력 계약 위반 시, “입력 오류”로 분류되어야 한다(표현/전달 방식은 시스템이 선택하되 *일관된 정책*으로 고정).
  - **No Solution**: 입력 계약은 만족하지만 어떤 조합으로도 마방진 불변식을 만족하는 채움이 불가능하면 “해 없음”으로 분류되어야 한다.
  - 두 오류는 **서로 다른 원인 범주**로 식별 가능해야 한다.
- **Expected Learning Outcome:**
  - Contract-first로 **경계 안정성**을 확보하고, 이후 리팩토링에서 “바뀌면 안 되는 것”이 무엇인지 명확히 한다.
  - 오류를 “입력 오류”와 “해 없음”으로 구분하는 사고를 학습한다.

### Stage 3: Domain Separation
- **Action:**
  - 도메인을 아래 책임 후보로 분해하고, 각 책임이 어떤 불변식/계약을 다루는지 매핑한다.
  - 경계(UI/입력 파싱/출력 포맷)와 도메인(검증/추론/해결)을 분리하는 선을 긋는다.
- **Thinking:**
  - “찾기(Blank/Missing)”, “검증(Validator)”, “해결 시도(Solver)”, “포맷(출력)”이 섞이면 테스트도 섞인다.
  - 불변식별로 책임을 분리하면, 실패 원인이 명확해지고 TDD RED가 더 작아진다.
- **Emotion:**
  - 구조가 생기면서 통제감 상승. 다만 “너무 쪼개는 것 아닌가” 불안이 잠깐 생김.
- **Pain Point:**
  - Solver가 검증과 탐색과 포맷까지 모두 떠안으면 리팩토링이 어려워진다.
- **Opportunity:**
  - Clean Architecture 관점에서 “도메인 규칙”을 중심에 두면, UI/Boundary는 바뀌어도 도메인은 보호된다.
- **Responsibility Separation:**
  - **BlankFinder**: 입력 그리드에서 빈칸(0) 좌표 2개를 식별
  - **MissingNumberFinder**: 1~16 중 누락된 2개 값을 산출
  - **MagicSquareValidator**: 그리드가 마방진 불변식(합=34 등)을 만족하는지 판정
  - **Solver**: 가능한 채움 조합을 생성하고 Validator로 검증하여 해를 선택
  - **Boundary/UI Adapter(후속 단계)**: 입력 계약 검증 결과 및 Solver 결과를 출력 계약 `int[6]`로 변환(도메인 밖)
- **Related Invariant:**
  - **INV-BLANK-COUNT-2**, **INV-VALUE-RANGE**, **INV-UNIQUE-NONZERO**
  - **INV-MAGIC-CONSTANT-34**
  - **INV-OUTPUT-FORMAT-6**, **INV-COORD-1INDEX**
- **Expected Learning Outcome:**
  - “기능 분해”가 아니라 **불변식/계약 단위의 책임 분해**를 익힌다.

---

### Stage 4: Dual-Track TDD Progress
- **Action:**
  - UI/Boundary 트랙과 Domain 트랙을 분리해 RED를 만든다.
  - GREEN에서는 “최소 통과”만 하고, REFACTOR는 계약을 깨지 않는 선에서 진행한다.
- **Thinking:**
  - Boundary RED는 “입력 계약/오류 정책/출력 포맷”을 고정하는 데 집중해야 한다.
  - Domain RED는 “불변식이 맞는지/해가 존재하는지”에 집중해야 한다.
- **Pain Point:**
  - UI/Boundary에서 도메인 실패를 처리하려 하거나, 도메인에서 에러 메시지/포맷을 결정하려는 유혹.
- **UI RED Focus:**
  - 입력 계약 위반 식별, 출력 포맷/1-index 준수
- **Logic RED Focus:**
  - BlankFinder/MissingNumberFinder/Validator/Solver 각각의 불변식 검증 포인트
- **GREEN Minimal Implementation Principle:**
  - 각 RED를 통과시키는 최소 규칙/최소 결정만 추가
- **REFACTOR Principle:**
  - 내부 구조 변경만 허용, **외부 계약 불변**
- **Expected Learning Outcome:**
  - 경계 vs 도메인 RED 구분, 계약/불변식의 지속 보호 학습

### Stage 5: Regression Protection
- **Regression Test Target:**
  - Edge case / Input error / Combination failure / Output format
- **Protected Contract or Invariant:**
  - 입력/출력/오류 계약, 합=34 불변식, 시도 순서 전략
- **Expected Learning Outcome:**
  - 회귀를 “케이스 추가”가 아니라 **계약/불변식 보호 강화**로 설계

### Background
- **Given** 4x4 행렬이 주어진다  
- **And** 0은 빈칸을 의미한다

- **And** 숫자는 1부터 16 사이여야 한다  
- **And** 0을 제외한 중복 숫자는 허용되지 않는다  
- **And** 4x4 마방진 상수는 34이다  
- **And** 출력 형식은 `[r1, c1, n1, r2, c2, n2]`이다

## 11. Final Summary
- **검증 결과:** 전반적으로 일관되며, 특히 **Boundary 입력 검증**과 **Solver reverse 시도(실패→재시도)**의 연결이 강합니다. 다만 Story 2~4의 시나리오 공백과 not-4x4 예외 누락으로 **일부 수정 필요**입니다.
- **가장 강한 부분:** SC-DOM-SOL-001이 **불변식(34) + 전략 불변식(실패 시 반대 조합)**을 동시에 검증하며, Output Contract까지 포함해 추적성이 좋습니다.
- **가장 약한 부분:** Story 2~4(Blank/Missing/Validator)가 **Scenario/RED ID로 아직 내려오지 못한 점**, 그리고 Error Contract/좌표 책임 경계의 표준화 부족입니다.
- **반드시 수정해야 할 항목:** (1) not-4x4 Boundary 시나리오 추가, (2) Story2~4용 Domain 시나리오 최소 세트 추가, (3) Error Contract와 좌표 변환 책임 경계 규칙 고정.
- **다음 단계로 진행 가능 여부:** **조건부 가능**. 위 “Missing Items”를 Scenario 레벨로 보강하면, RED Test ID와 Implementation Task로 **무리 없이 분해 가능한 상태**가 됩니다.
