## 1. Executive Summary

MagicSquare_xx는 “4×4 마방진을 완성하는 프로그램”을 만드는 프로젝트가 아니라, **마방진 유효성 판정의 불변식과 입·출력 계약을 먼저 고정하고, 이를 Dual-Track TDD로 검증 가능하게 만드는 훈련용 제품/학습 시스템**이다.

본 PRD는 구현 전에 다음을 확정한다.

- **무엇을 보장하는가**: 입력/출력/오류 계약, 불변식, 결정성, 회귀 보호
- **무엇을 하지 않는가**: 단일 정답 격자 고정, 퍼즐 UX/난이도/힌트, 전체 해 나열, 최적화 중심의 범위
- **어떻게 검증하는가**: Dual-Track(UI 계약 vs Domain 규칙)로 요구↔검증을 1:1 추적

---

## 2. Vision & Intent

### 2.1 Vision

**불변식 중심 설계 → 계약 고정 → Dual-Track TDD → 리팩토링 → 회귀 보호**로 이어지는 학습 루프를 구축한다.

### 2.2 Product Intent (What we are building)

- 사용자는(호출자는) **4×4 입력 격자**를 전달한다.
- 시스템은 **계약에 따라** 입력을 거부하거나, **해결 결과 또는 실패 유형**을 반환한다.
- 결과는 “특정 격자와의 일치”가 아니라 **불변식/계약을 만족하는지**로 정의된다.

---

## 3. Background / Why Now

### 3.1 Background

4×4 마방진은 규칙(합, 값 집합, 대각선 포함)이 명확해 **오라클 설계와 회귀 검증**을 훈련하기 좋은 도메인이다. 동시에 다해/동형의 함정이 있어, “완성/정답” 중심 정의는 쉽게 범위를 폭발시킨다.

### 3.2 Why now (What must be closed before implementation)

구현 전에 반드시 닫아야 할 것:

- **“맞다”의 정의**를 단일 격자 스냅샷이 아니라 **불변식(규칙 통과)**으로 고정
- 입력/출력/오류의 **계약을 문장 수준이 아니라 테스트 가능한 형태**로 고정
- Dual-Track에서 **Boundary 책임(형식·조기거부) vs Domain 책임(최종 판정)**을 분리

---

## 4. Problem Definition

### 4.1 Anti-definition (do not use)

- “4×4 마방진을 완성하는 프로그램을 만든다.”

이 정의는 “완성”에 과도하게 초점을 둬 검증/회귀를 부수적으로 만들고, 단일 정답 오해 및 범위 폭발(생성·UI·힌트 등)을 유발한다.

### 4.2 Correct definition (this PRD’s definition)

- **4×4 격자와 1~16 배치(및 2빈칸 퍼즐 입력)에 대해, 유효성 판정 규칙과 입·출력 계약을 명시하고, 그 판정이 반복 가능하게 검증되도록 요구·검증을 동시에 고정하는 제품/학습 과제이다.**

---

## 5. Goals & Non-goals (Scope)

### 5.1 Goals

- **G1. 불변식 기반 요구 고정**: 핵심 Invariant를 표로 정의하고, 계약과 연결한다.
- **G2. 계약 기반 기능 제공**: 입력/출력/오류 계약을 외부에 보장한다.
- **G3. Dual-Track 검증 가능성**: UI(Boundary)와 Domain(Logic)의 테스트를 분리해 회귀를 보호한다.
- **G4. 리팩토링 안전성**: 외부 계약이 불변인 상태에서 내부 구조를 개선할 수 있게 한다.

### 5.2 Non-goals

- **NG1. 단일 정답 격자 고정/일치 요구**
- **NG2. 퍼즐 UX(힌트/난이도/대화형 입력)**
- **NG3. 모든 유효 배치 나열/개수 산출**
- **NG4. 성능 최적화 중심의 구현**

## 6. Personas & Assumptions

### 6.1 Primary persona (current)

- QA/학습자(혹은 팀 과제 수행자): 요구를 테스트 가능하게 고정하고, 회귀/실패 모드를 분류하며, 리팩토링을 안전하게 수행하고자 한다.

### 6.2 Assumptions

- A1. “정답”은 단일 배열이 아니라 **규칙 통과**로 정의된다.
- A2. 외부 호출자는 UI/CLI/API일 수 있으나, 본 PRD의 계약은 **경계에 독립적**(입출력 스키마 중심)이다.

## 7. User Journey (5 stages)

1. **Problem Recognition**: “정답 구현”이 아니라 “불변식 기반 설계 훈련”으로 재프레이밍
2. **Contract Definition**: Input/Output/Error 계약을 구현보다 먼저 고정
3. **Domain Separation**: 책임(빈칸/누락수/판정/해결)을 분리
4. **Dual-Track TDD Progress**: Boundary RED vs Domain RED 분리 진행
5. **Regression Protection**: 정상/오류/조합 실패/포맷 회귀를 계약/불변식에 연결해 보호

## 8. Epics / User Stories

본 PRD의 핵심 사용자 스토리(요약):

- **MS-US-01 입력 검증 (Boundary)**: 계약 위반 입력을 조기 거부하고 Domain을 호출하지 않는다.
- **MS-US-02 빈칸 좌표 탐색 (Domain)**: 빈칸 2개를 row-major로 식별한다.
- **MS-US-03 누락 숫자 탐색 (Domain)**: 0을 제외하고 누락된 2개 숫자를 오름차순으로 찾는다.
- **MS-US-04 마방진 검증 (Domain)**: 완성 격자가 마방진 규칙을 만족하는지 판정한다.
- **MS-US-05 두 조합 시도 (Domain + Output Contract)**: 규칙에 따라 두 배치를 결정적으로 시도하고 결과를 계약 포맷으로 반환한다(불가 시 실패).

## 9. Functional Requirements

### 9.1 MVP definition (this PRD’s MVP)

**MVP는 “2빈칸(0) 퍼즐 입력을 받아, 계약에 맞는 해결 결과 또는 오류를 반환하는 기능”**으로 정의한다.  
단, 제품의 목적은 알고리즘 성취가 아니라 **불변식/계약/회귀 보호를 달성하는 것**이며, 요구 충족은 검증(테스트/추적성)으로 판단한다.

### 9.2 Input Contract

입력은 `int[4][4]` 격자이며, 다음을 만족해야 한다.

- `0`은 빈칸을 의미한다.
- 빈칸(`0`)은 **정확히 2개**여야 한다.
- 모든 값은 `{0} ∪ {1..16}` 범위여야 한다.
- `0`을 제외한 값은 **중복되면 안 된다**.

### 9.3 Output Contract (Success)

성공 시 결과는 아래 형식이다.

- `int[6] = [r1, c1, n1, r2, c2, n2]`
- 좌표 `(r1,c1)`, `(r2,c2)`는 **1-index**, 각 값은 `[1..4]`
- `(r1,c1)`는 입력에서 row-major 스캔으로 찾은 **첫 번째 빈칸**, `(r2,c2)`는 두 번째 빈칸
- `n1`, `n2`는 `[1..16]`, `n1 != n2`
- `{n1,n2}`는 입력에서 누락된 수 집합과 동일

### 9.4 Error Contract (Failure)

실패는 최소 다음 범주를 구분한다.

- **Validation failure**: 입력 계약 위반 (차원/빈칸 수/값 범위/중복)
- **No solution failure**: 입력은 계약을 만족하지만, 주어진 빈칸에 유효한 완성이 존재하지 않음

오류는 `errorCode`와 고정 `message` 매핑을 갖는다(문구/코드 변경은 회귀를 깨므로 금지).

## 10. Invariants (Product Guarantees)

### 10.1 Partial input invariants (P-*)

- **P-1**: 4×4 차원
- **P-2**: 빈칸(0) 정확히 2개
- **P-3**: 0이 아닌 값 범위 1..16
- **P-4**: 0 제외 중복 없음

### 10.2 Completed grid invariants (I-*)

완성 격자가 “마방진”으로 판정되려면:

- **I-1**: 4×4, 16칸
- **I-2**: 각 칸 1..16
- **I-3**: 1..16이 각각 1회
- **I-4~I-7**: 행 4/열 4/대각 2의 합이 동일하며, 매직 상수는 34

### 10.3 Output invariants (O-*)

성공 결과는 Output Contract의 제약을 만족해야 한다(길이/좌표/값/집합/빈칸 좌표 일치).

### 10.4 Meta invariants (M-*)

- **M-1 결정성**: 동일 입력은 동일 출력/동일 실패를 만든다.
- **M-2 입력 의존**: 외부 상태(I/O, 시간, 랜덤)에 의존하지 않는다.
- **M-3 근거 제한**: “유효” 판정은 정의된 불변식과 계약에만 근거한다(숨은 규칙 금지).

## 11. Architecture Principles (High-level)

### 11.1 ECB (boundary/control/entity)

- **Allowed dependency**: `boundary -> control -> entity`
- **Forbidden**: `entity -> boundary/control`, `control -> boundary`

### 11.2 Clean Architecture intent

- Domain 규칙(불변식/판정/결정 규칙)은 외부 입출력에서 분리한다.
- Boundary는 입력 파싱/계약 수준 조기 거부, 출력 포맷/오류 스키마 표준화를 담당한다.

---

## 12. Verification Strategy (Dual-Track)

### 12.1 Dual-Track definition

- **Logic Track**: 불변식/결정성/출력 계약의 핵심을 Domain 테스트로 보호
- **UI Track**: Domain을 Mock하고, Input/Output/Error 계약을 Boundary 테스트로 보호

### 12.2 Traceability (Requirement → Verification)

모든 핵심 Invariant/Contract는 최소 1개 이상의 검증 항목(테스트/체크리스트)에 연결되어야 한다.

---

## 13. Quality Requirements (Quality Bar)

- **결정성**: 동일 입력 → 동일 결과 (M-1)
- **회귀 보호**: 계약 포맷/에러 문구/출력 순서 변경은 금지(변경 시 Major로 취급)
- **커버리지 목표(가이드)**:
  - Domain Logic ≥ 95%
  - UI Boundary ≥ 85%
  - Data ≥ 80% (데이터 레이어가 포함될 경우)
- **금지 패턴(요약)**: `print()`, bare `except:`, 매직 넘버/문자열 남발, 테스트 약화

---

## 14. Risks / Open Questions

### 14.1 Key risks

- “완성” 중심으로 요구가 이동하며 범위가 폭발할 위험
- 단일 스냅샷 기대값 고정으로 다해/동형과 충돌할 위험
- Validation failure와 No solution failure의 표현이 섞여 UX/검증이 흔들릴 위험

### 14.2 Open questions (must decide in PRD before implementation)

- **Q1**: Application 레이어 분리 여부(UseCase 서비스 도입)
- **Q2**: 성공 응답 형태: raw `int[6]` 유지 vs 래핑(`{result: ...}`)
- **Q3**: (선택) 영속화가 필요하다면 파일 포맷(JSON vs CSV)
