## STEP 1 — Observation (관찰)

### 1.1 현재 우리가 해결하려는 상황은 무엇인가?

**관찰된 상황**

한 QA 엔지니어가, **아직 구체화되지 않은 소프트웨어 과제**를 맡은 초기 단계에 있다. 과제의 주제는 「4×4 격자에 1~16을 한 번씩 배치했을 때, 행·열·대각선의 합이 모두 같아지는 배치」와 관련된 **규칙·불변조건·정답 여부**이다. 저장소만 존재하고 산출물은 없으므로, **요구·사용자·실행 환경·성공 기준**은 아직 미정이다.

**해결 대상 (관찰)**

「마방진 하나」가 아니라, 대략 다음과 같은 **불명확한 문제 영역**이다.

- **무엇을** 만들 것인가: 생성기, 검증기, 퍼즐 UI, 학습용 데모, 테스트 대상 모듈 등
- **누가** 쓰는가: 본인 학습, 팀 과제, 면접, 교육용 등
- **어떤 품질**을 기대하는가: 「하나의 예시만 나오면 됨」 vs 「모든 해·특정 해·랜덤 해」 vs 「잘못된 입력에 대한 거부」 등

**관찰 요약**

「4×4 + 마방진 규칙」이라는 **수학적·논리적 제약이 있는 작은 도메인**을, **검증 가능한 프로그램**으로 옮기려는 의도가 있고, 그 전에 **문제를 어떻게 정의할지**부터 맞추려는 단계이다.

### 1.2 왜 4×4 마방진 문제를 다루는가?

| 관찰 | 해석 |
|------|------|
| **크기가 4×4** | 3×3보다 제약·케이스가 늘지만, 5×5 이상보다 **수동 검증·테스트 설계**가 여전히 가능한 중간 규모 |
| **역할이 QA** | 정답/오답이 **명확한 오라클**(행·열·대각 합, 1~16 중복 없음 등)이 있어 **테스트 케이스·경계값·회귀** 연습에 적합 |
| **짝수 차 (n=4)** | 홀수 차와 달리 **한 가지 공식만으로 끝나지 않음** → 요구를 어떻게 좁힐지 스스로 정해야 하는 상황이 자주 생김 |
| **프로젝트명 MagicSquare_xx** | 학습/실습·포트폴리오·과제 템플릿 중 하나로 보이며, **xx**는 변형·확장을 암시할 수 있음 |

**관찰적 서술**

4×4는 **제약이 분명하고**, **QA 관점에서 검증 규칙을 문장·테스트로 쓰기 쉬우며**, 동시에 **생성/탐색 방식이 여러 갈래**라서 「요구를 먼저 고정하지 않으면 범위가 넓어지는」 전형적인 연습·과제 주제이다. 수학적 호기심뿐 아니라 **「정의된 규칙 ↔ 관찰 가능한 출력 ↔ 자동 검증」**을 연결하는 **연습 장**으로 자주 선택된다.

### 1.3 어떤 학습·시스템 설계 맥락에서 등장하는가?

**학습 맥락**

- **알고리즘·CS 기초:** 백트래킹, 제약 만족, 순열/조합, 불변조건 유지
- **수학·퍼즐:** 조합론, 대칭·동형, 짝수 차 마방진의 특수 규칙
- **QA·테스트:** 명세 기반 테스트, 오라클 설계, 경계값, 회귀
- **요구공학 입문:** 「마방진 프로그램」 한 문장이 생성/검증/편집/힌트 등으로 갈라지는 경험

**시스템 설계 맥락 (아직 시스템 없음)**

- **도메인 코어:** 「유효한 4×4 배치인가?」 — 순수 규칙·판정
- **애플리케이션 경계:** CLI / API / UI / 라이브러리 — 미정
- **비기능:** 성능, 결정성, 오류 메시지 품질 — QA가 다루기 쉬운 축

**상황을 관찰 언어로 서술**

「4×4 격자 + 합 일치 + 숫자 1~16 한 번씩」이라는 **관찰 가능한 현상**을, 나중에 프로그램 요구로 옮길 **후보 현상**으로 두고 있는 상태이다. 「마방진을 만든다」가 아니라 **문제를 관찰하는 단계**에 가깝다.

### 1.4 STEP 1에서 아직 보이지 않는 것

- 최종 사용자 (본인 / 채점 시스템 / 다른 개발자)
- **생성** vs **검증** vs **둘 다**
- 표준 마방진 하나 vs 모든 해·랜덤 해
- 잘못된 입력·부분 입력·대화형 수정 여부

## STEP 2 — Why #1

### 2.1 질문

**Q:** 왜 마방진을 완성해야 하는가?

### 2.2 가정한 답 (A)

> **「4×4 격자에 1~16을 채워 행·열·대각선 합이 모두 같게 만든 ‘유효한 배치’를 얻어야, 그 결과가 규칙을 만족하는지 자동으로 검증·시연할 수 있기 때문이다.」**

완성의 목적은 퍼즐 재미가 아니라, **명확한 오라클을 가진 작은 도메인**에서 **「정답 산출물」과 「검증 로직」**을 함께 다루는 QA·학습 과제를 진행하기 위함이라고 가정한다.

### 2.3 A에서 드러나는 불편함·구조적 문제

#### (1) 「완성」과 「검증」의 목적 겹침·어긋남

- A는 **완성된 격자**가 필요하다고 하지만, QA 핵심은 종종 **검증기**이다.
- 「만들기」와 「맞는지 확인하기」가 한 프로젝트에 있으면 실패 원인 추적이 어렵다.
- **불편:** 답이 사실상 「검증하려면 샘플이 필요해서」인데, 요구 문장이 「완성」이면 설계·일정이 **생성 중심**으로 기울 수 있다.

#### (2) 「완성」 하나에 여러 성공 기준이 묶임

- 임의의 유효 마방진 하나 / 특정 패턴 / 모든 해 / 사용자 퍼즐 완료 등이 구분되지 않음.
- **구조적 문제:** 범위 폭발, 비결정성·동형 해 이슈.

#### (3) 4×4·짝수 차와 A의 긴장

- 유효 배치가 **여러 개** → 「완성 = 단일 정답」이 아님.
- **구조적 문제:** 오라클은 단순하지만 **기대 격자 하나로 고정**하기 어렵다 (스냅샷 테스트 취약).

#### (4) 완성이 필수 경로인지 불명확

- 골든 격자 fixture + 검증만으로도 상당 부분 목적 달성 가능.
- **불편:** A가 **과잉 정당화** → 불필요하게 어려운 생성 문제까지 끌어올 위험.

#### (5) 학습·시연 맥락의 완료 정의 분열

- 「유효 격자 1개」 / 「모든 테스트 통과」 / 「사용자 퍼즐 완료」가 경쟁.
- **구조적 문제:** 산출물 중심 vs 규칙·테스트 중심의 **완료 판단 흔들림**.

#### (6) 이해관계자·가치 충돌이 숨음

- 빠른 종료 vs 깊은 학습 vs 과제 제출 기준이 다름.
- 「왜 완성?」이 기술적 이유만 있으면 **누구를 위한 완성인지**가 미뤄짐.

### 2.4 Why #1 정리

| 핵심 긴장 | 내용 |
|-----------|------|
| 수단·목적 | 완성(수단) vs 검증·학습(목적) 역전 위험 |
| 단일 표현 | 「완성」 뒤의 다중 요구 |
| 다해·동형 | 단일 골든 vs 유효성 오라클 충돌 |
| 범위 | 완성 없이도 요구 상당 부분 달성 가능 |
| 완료 정의 | 격자 산출 / 테스트 / UX 분열 |

## STEP 3 — Why #2

### 3.1 질문

**Q:** 왜 단순 계산이 아니라 프로그램으로 구현하는가?

### 3.2 반복 가능성

**답:** 행·열·대각 합, 1~16 중복 없음 등을 **매번 같은 절차·같은 기준**으로 확인해야 한다. 손계산은 케이스가 늘면 절차·피로에 따라 달라진다. 프로그램은 **동일 규칙 적용을 N번 복제**한다.

**구조적 문제**

- 반복 ≠ 자동 (환경·버전·입력 형식)
- 4×4 다해 → **「규칙 통과」**로 반복성을 정의해야 함
- 소수 케이스는 손계산이 더 빠를 수 있음

### 3.3 검증 자동화

**답:** 오라클을 기계가 실행한다. 유효/무효를 명확히 내리고, 깨진 격자·경계값을 스위트에 넣고 **회귀**한다.

**구조적 문제**

- 「프로그램」이 곧 **생성까지**로 확장되기 쉬움
- 잘못된 검증 로직이면 일괄 오판
- 자동화 전제로 **테스트 데이터 설계** 필요

### 3.4 오류 방지

**답:** 합산 실수, 칸 누락, 중복, 대각선 누락을 줄이고, 규칙을 한곳에 모아 **일관된 실패 보고**로 수정 지점을 좁힌다.

**구조적 문제**

- 사람 실수 → **구현 버그**로 이전 가능
- 검증 없는 생성은 「프로그램이 출력 = 맞다」 함정
- 오류 유형(입력 / 규칙 / 구현) 구분 필요

### 3.5 규칙 기반 사고 훈련

**답:** 「합이 같다」를 불변조건·전제·예외로 쪼개 **명세 → 조건 → 테스트** 흐름을 연습한다.

**구조적 문제**

- 규칙 과소/과대 명세
- 암묵 규칙이 기대에 숨음
- 도메인 훈련 vs 기술 스택 훈련 혼선

### 3.6 Why #2 통합

| 관점 | 단순 계산 한계 | 프로그램이 주는 것 |
|------|----------------|-------------------|
| 반복 가능성 | 피로·절차 편차 | 동일 규칙 N회 |
| 검증 자동화 | 회귀·대량 케이스 부담 | 오라클·테스트 실행 |
| 오류 방지 | 합산·누락·중복 실수 | 규칙 일원화·진단 |
| 규칙 기반 사고 | 결과 중심 | 명세·조건·테스트 분해 |

**한 줄:** 손계산은 **한 격자·한 번**에는 충분하나, **재현성·회귀·명세화**가 필요한 QA·학습 맥락에서는 실행 가능한 검증 로직(프로그램)이 합리적이다. **최소 책임은 검증**일 수 있다.

### 3.7 설계 전 질문 (구현 아님)

1. 프로그램 최소 책임: 검증만 vs 생성까지?
2. 반복 기준: 출력 동일 vs 규칙 통과?
3. 자동화 1차 사용자: 본인(테스트) vs 외부 사용자?
4. 규칙 훈련 vs 코딩 연습 중 무엇이 목표?

## STEP 4 — Why #3 (핵심 발견)

### 4.1 질문

**Q:** 왜 이 문제를 TDD 방식으로 설계하려 하는가?

### 4.2 무엇이 통제되어야 하는가?

| 통제 대상 | TDD에서의 형태 |
|-----------|----------------|
| 「맞다」의 정의 | 테스트가 합격/불합격 선언 |
| 규칙 적용 범위 | 케이스가 검사 항목 목록 |
| 범위(스코프) | 한 번에 하나의 행위만 red → green |
| 회귀 | 기존 테스트가 안전망 |
| 완료 판단 | 전 테스트 green을 완료 조건 후보 |

**핵심 발견:** 통제 중심은 **「16칸 배열 자체」**가 아니라 **「유효성 판정 로직과 그 증거(테스트)」**이다. **「동일 출력」**이 아니라 **「규칙 통과」**를 통제 단위로 명시해야 다해·비결정성과 충돌하지 않는다.

### 4.3 어떤 불변 조건이 존재하는가?

**수학·도메인 층 (완전히 채워진 4×4)**

- 크기 4×4, 16칸
- 값 1~16, 중복·누락 없음
- 행 4, 열 4, 주·부대각선 합이 모두 동일 (4×4·1~16에서는 34)

**명세 층**

- 빈 칸 허용 여부
- 범위 밖·중복·비정수 입력 처리
- 회전·반사 동형을 같은 해로 볼지 여부

**메타 층**

- 동일 입력 → 동일 판정 (순수·결정적 검증)
- 무효 시 위반 규칙 식별 (선택)

**핵심 발견:** 불변조건이 수학층과 명세층으로 나뉜다. **유효성 불변을 먼저**, 동형·생성은 나중이 안전하다. 약한 불변(행 합만)으로 green하면 **가짜 마방진** 통과 위험이 있다.

### 4.4 왜 입력/출력이 명확해야 하는가?

TDD는 **고정 입력 → 기대 출력(또는 기대 실패)** 없이 red/green이 성립하지 않는다.

**입력 명확성**

- 테스트가 문서·fixture가 됨
- 실패 재현·경계 케이스 분리
- 파싱 실패 vs 규칙 실패 책임 분리

**출력 명확성**

- 최소: 유효 여부 (boolean 수준의 판정)
- 확장: 위반 목록 (진단)
- 생성: 특정 16칸 고정보다 **「규칙 통과」** 기대가 다해와 정합적

**핵심 발견:** I/O가 흐리면 TDD가 「돌려 보고 눈으로 확인」으로 퇴행한다. Why #2의 자동화·반복 가능성도 붕괴한다.

### 4.5 Why #3 통합 문장

> **4×4 마방진은 불변조건이 명확한데 정답 격자는 하나가 아니므로, 「완성」보다 「규칙 통과 여부」를 먼저 테스트로 고정해야 하고, TDD는 그 규칙·범위·회귀를 통제하면서 구현이 검증기에서 생성기로 넘어가지 않게 하는 설계 방식이다.**

### 4.6 TDD 선택 시 주의 (구현 전)

1. 테스트 먼저 ≠ 생성 먼저 — 첫 red는 유효성 판정이 Why #1·#2와 정합적
2. 약한 테스트로 green → 불변조건을 단계적으로 강화할 계획 필요
3. 특정 16칸 스냅샷은 다해와 충돌
4. 테스트 이름·케이스가 **살아 있는 명세**가 되도록 의도

## STEP 5 — 진짜 문제 정의

### 5.1 표면 문제 정의 (잘못된 정의)

> **「4×4 마방진을 완성하는 프로그램을 만든다.」**

| 문제 | 설명 |
|------|------|
| 목적이 산출물에 고정 | 검증·명세가 부수적 |
| 단일 정답처럼 읽힘 | 다해·동형 무시 |
| 범위 비대 | 생성·UI·힌트까지 포함 가능 |
| 완료 기준 모호 | 「돌아감」 vs 「규칙 충족」 |
| QA·TDD 맥락 소실 | 손으로 한 장 맞추기와 동일시 |

**착각:** 문제 = 퍼즐 풀기, 소프트웨어 = 자동화.

### 5.2 개선된 문제 정의 (정확한 정의)

> **「4×4 격자와 1~16 배치에 대해, 마방진으로서의 유효성(값 집합·행·열·대각선 합 일치)을 명시된 규칙으로 판정하고, 그 판정을 반복 가능하게 검증할 수 있도록 요구를 고정·테스트·회귀 가능한 형태로 다루는 과제이다. 필요 시, 규칙을 만족하는 유효 배치를 산출하는 기능은 그 판정이 안정된 이후의 확장 범위로 둔다.」**

| 요소 | 명시 |
|------|------|
| 핵심 가치 | 맞는지 판정 + 판정 규칙 고정 |
| 도메인 | 4×4, 1~16, 완전히 채워진 배치 |
| 1차 성공 | 규칙 통과 — 특정 한 장과 일치 아님 |
| 방법론 | 테스트 가능 분해·회귀 |
| 범위 | 검증 1차, 산출 2차 |

**한 줄:** 푸는 문제는 **「마방진 만들기」**가 아니라 **「마방진인지 판단 기준을 신뢰할 수 있게 만드는 것」**이다.

### 5.3 핵심 Invariant

#### 구조·값

| ID | 불변 조건 |
|----|-----------|
| I-1 | 4행 4열, 16칸 |
| I-2 | 각 칸 ∈ {1,…,16} 정수 |
| I-3 | 1~16 각각 정확히 한 번 (중복·누락 없음) |

#### 매직 합

| ID | 불변 조건 |
|----|-----------|
| I-4 | 네 행의 합 동일 |
| I-5 | 네 열의 합 동일 |
| I-6 | 주·부대각선 합이 행·열과 동일 |
| I-7 | 행 4 + 열 4 + 대각 2 = 하나의 상수 (4×4·1~16에서는 34) |

#### 메타 (판정·과제)

| ID | 불변 조건 |
|----|-----------|
| M-1 | 동일 완전 배치 → 동일 판정 |
| M-2 | 판정은 배치 내용만 의존 |
| M-3 | 「유효」는 I-1~I-7에만 근거 |

#### 의도적 제외 (핵심 Invariant 아님)

- 특정 한 장과 동일
- 회전·반사 동형 동일 취급 (별도 정책)
- 구성 경로·방법

### 5.4 실제로 훈련하려는 사고 능력

| # | 능력 | 요약 |
|---|------|------|
| 1 | 명세 분해 | 「합이 같다」→ 검사 가능 조건; 완성/맞음/끝남 분리 |
| 2 | 오라클 설계 | 규칙 전체 기준; 유효·무효·거부 구분 |
| 3 | 불변조건 우선 | 기능 전 성질 목록; 약한 vs 강한 조건 |
| 4 | 범위·우선순위 | 1차 판정 vs 2차 산출·UI |
| 5 | 테스트 주도 요구 고정 | 실패·성공 시나리오 선행; 회귀 의식 |
| 6 | 실패 모드 분류 | 무효 / 입력 / 명세 / 구현 버그 구분 |
| 7 | 다해·동형 계약 | 유일 출력 기대 금지; 동일 vs 동치 분리 |

### 5.5 정의 대조

| 구분 | 표면 | 개선 |
|------|------|------|
| 초점 | 완성된 마방진 | 유효성 판정·기준 고정 |
| 성공 | 표 하나 | 판정 일관·테스트 통과 |
| 정답 | 한 장 | 규칙 만족 모든 배치 |
| 방법 | 만들고 눈으로 확인 | 명세·불변·시나리오 선행 |
| QA 역할 | 부가 | 판정·회귀·범위가 중심 |

### 5.6 범위 선언 (설계 아님)

**In scope**

- 완전히 채워진 4×4에 대한 유효성 판정 규칙
- 규칙의 명시·테스트·회귀
- 유효/무효·대표 위반 유형에 대한 판단 일관성

**Out of scope (1차 목표 아님)**

- 특정 한 장만을 정답으로 하는 기대
- 사용자 퍼즐·힌트·난이도
- 모든 유효 배치 나열·개수 (별도 과제)
- 구성 방식·속도·최적화
